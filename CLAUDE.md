# Repo handoff — ya_game

Two independent Unity projects, one git repo, GitHub remote
`https://github.com/folzy1092/Yandex-Game.git`, both targeting Yandex Games
(WebGL, ad-revenue monetisation via the Yandex Games SDK).

- **DroneStrike/** — FPV kamikaze-drone strike simulator. Active development.
- **EpicBattle3D/** — CS-style free-for-all shooter with bots. Built and
  stable, currently paused (user's call, not abandoned).

Each has its own `README.md` with build/run instructions specific to it —
read that before touching either project. This file is the cross-cutting
context: how work actually gets done here, and what a fresh session needs to
know before making changes.

## There is no Unity in this environment

Whoever is editing code here (Claude or otherwise) has no Unity Editor, no
compiler, no way to press Play. The user runs Unity themselves in a separate
local project folder and reports back screenshots and console output. Every
change ships unverified except by what can be checked without Unity:

- **Brace/paren/bracket balance** across every `.cs` file — cheap, catches
  the dumbest class of typo. There's a throwaway checker script pattern used
  repeatedly this project (strip comments/strings via regex, count
  delimiters); rebuild it in the session's scratchpad rather than hunting for
  a prior copy, it's ~20 lines.
- **Replaying procedural-generation logic in Python** before trusting it. The
  mission scene builder (`MissionBuilder.cs`) does rejection-sampling
  placement with a fixed seed — when changing placement radii, target counts,
  or map sizes, mirror the logic in a quick Python script and run it against
  the *actual* production seed (not a random one) to confirm nothing gets
  silently dropped. This caught several real bugs blind (a self-overlapping
  claim-line bug, a map that reliably dropped one target on the real seed,
  integer-division that bunched patrol trucks onto adjacent corners instead
  of spacing them around the loop).
- **Parsing a downloaded glTF/GLB's own accessor bounds** to determine a
  model's actual axis extents (nose-to-tail axis, native pivot location)
  instead of guessing rotation/scale blind. A GLB is `glTF` + version + length
  header, then chunks; the JSON chunk has `accessors[].min`/`.max` per
  `VEC3` position accessor — union them for the model's true bounding box.
  This turned a second blind guess at warhead orientation into a correct
  first-principles fix (see DroneStrike section below).

**Every change gets synced into the user's live Unity project folder**
(`C:\Users\Folzy\Desktop\DroneStrike\Assets\...` /
`C:\Users\Folzy\Desktop\EpicBattle3D\Assets\...`) after editing the repo
copy, via `cp -rf` of `Scripts/`, `Editor/`, and any new `Resources/Models`
or `Resources/Textures` files. **Never wipe the destination `Resources/`
tree wholesale** — Unity-generated `Materials/` and `Textures/` subfolders
live only in the local project (untracked, regenerated by the `1 - Generate
Materials` editor command) and wiping them forces a full rebuild. Copy over
the top; don't `rm -rf` the destination first.

After syncing, tell the user which editor command to re-run
(`Tools → Drone Strike → BUILD EVERYTHING`, or the equivalent) — nothing
takes effect until they do, and scene-generation logic changes need a full
rebuild, not just a script recompile.

## Asset sourcing

Both projects use models/textures/sounds sourced two ways:

1. **Generated procedurally at build or run time** — the large majority.
   Textures via `ProceduralTextures.cs`, sounds via `ProceduralAudio.cs`
   (synthesised from noise/sine/envelopes, no imported audio files), meshes
   via primitives or the small custom mesh-building helpers
   (`PrimitiveMesh.cs` — frustums/cones, tapered propeller blades, a
   double-sided sagging cloth mesh).
2. **Downloaded real models**, when procedural attempts kept failing visually
   (a warhead nose that read as anatomically wrong through two rounds of
   hand-tuned primitive geometry; a camo net that was flat-out *broken*, see
   below, not just ugly). Sourced via the in-app browser tool from
   **poly.pizza** (search → open model page → the page embeds a
   `<model-viewer src="https://static.poly.pizza/....glb.br">`; despite the
   `.br` extension the server serves it uncompressed over a plain `curl` with
   no special headers — `curl -o file.glb <that url>` just works, verify with
   `xxd` that it starts with the `glTF` magic bytes) and occasionally
   **kenney.nl** (CC0, direct zip downloads, used for particle sprites —
   `Assets/Resources/Textures/Particles/`). Every downloaded asset is
   licensed CC0 or CC-BY and logged in `DroneStrike/CREDITS.txt` with
   source URL and license — keep that file in sync when adding another one.

   A downloaded model's scale, pivot and rest orientation are unknown until
   someone actually sees it rendered. The established pattern:
   `NormalizeModelSize` (rescale to a known real-world footprint from the
   measured bounds), `RecentreModelOnGround` (shift so the footprint is
   centred horizontally and sits at the root's origin vertically — a model
   is *not* usually authored with its geometry centred on its own file
   pivot, and leaving it wherever the file's pivot happened to be is what
   made a tent's visible mesh drift away from its own placement/highlight
   marker). Document the calibration constants inline and expect one
   round-trip of user screenshot → constant tweak, same as any blind 3D
   integration — except see the glTF-accessor-parsing trick above, which
   skips that round-trip when it's feasible.

## DroneStrike-specific notes

Read `DroneStrike/README.md` first — it has the full build steps, controls,
and a running "what to check after a rebuild" list that gets appended to
after every fix pass. The condensed extra context a fresh session won't get
from the README alone:

- **Scene generation is entirely code-driven.** `Editor/MissionBuilder.cs`
  builds all three mission scenes from one `Profile` struct (per-map size,
  target counts, ground/road materials, lighting) rather than three
  hand-built scenes — a fix to placement logic applies to all three at once.
  `Editor/MainMenuBuilder.cs` builds the menu scene the same way.
  `Editor/DroneBuildSetup.cs`'s `BUILD EVERYTHING` command runs materials
  generation, all mission scenes, the menu scene, and build-settings setup
  in one pass — that's the only thing the user needs to re-run after a sync.
- **Placement is rejection sampling against a claim list**, not hand-picked
  coordinates: everything (targets, field works, clutter, patrol road)
  registers the ground it occupies as a circle (or a chain of circles for
  long thin objects like berms), and later placements sample until they find
  unclaimed ground clear of the road. Reorder-sensitive: place the largest,
  pickiest footprints first (this project learned that the hard way — tents
  placed last on a tight map kept failing to find room; reordered to
  largest-radius-first and it stopped).
- **A mesh built with `RecalculateNormals()` and *shared* vertices carrying
  triangles in both winding directions will render solid black.** This is
  the actual, confirmed root cause behind a camo net and a grass patch that
  both rendered as flat black shapes for multiple fix-attempts before the
  real bug was found: `RecalculateNormals` averages every triangle a vertex
  touches into one normal, and a vertex touched by both an "up" triangle and
  a "down" one averages towards zero — a near-zero normal lights as though
  it faces away from every light in the scene. Fix: either don't make
  something double-sided that way (single-sided solid geometry, like the
  propeller blades, is unaffected), or give each side of a double-sided
  sheet its own *separate* vertex copies with explicitly-computed opposing
  normals (see `PrimitiveMesh.Drape`) rather than relying on
  `RecalculateNormals` across shared ones.
- **Two kinematic Rigidbodies never push each other apart** — Unity does not
  resolve kinematic-vs-kinematic collisions at all. `PatrolMover` (patrol
  trucks) has to explicitly check for another `Target` ahead and react
  (reverse direction) itself; nothing physics-based will do it for free.
- **Damage-visual states must be visually distinct from each other**, not
  just distinct in principle: "damaged but alive" and "destroyed" used
  near-identical dark colours at one point and were indistinguishable from
  any real distance, which read as a game bug ("looks dead, keeps fighting")
  rather than a design choice.
- **Warhead orientation** (`DroneFactory.BuildWarheadView`,
  `WarheadModelPitch/Yaw/Roll` constants): currently believed correct,
  derived from the GLB's own parsed accessor bounds rather than guessed —
  see the glTF-parsing note above for the technique if it's ever wrong again
  or a different model gets swapped in.
- **Balance knobs**: `DroneStrike/README.md` has a full table
  ("Настройка баланса"). The signal range (`SignalLink.cleanRange` /
  `maximumRange`) and the launch-pad ring radius in `MissionBuilder.cs` are
  *coupled* — changing one without re-checking the other against the map
  sizes can make the far side of a map unreachable before the signal even
  degrades. Verify offline (compute worst-case pad-to-target distance per
  map profile) before committing a change to either.

## Git / workflow conventions already established here

- Commits are created when explicitly asked, never silently. Commit messages
  explain *why* (the failure mode a fix addresses, the reasoning behind a
  design choice), not just what changed — the diff already shows what.
- No force-push, no `--no-verify`, no destructive git operations without
  explicit ask.
- The user communicates in Russian, terse, often with in-game screenshots as
  the primary bug report — read the screenshot content carefully before
  proposing a fix; several "the same bug" reports across this project turned
  out to be different objects being misidentified (a flat camo-net sheet
  mistaken for "two tents", a patrol truck mistaken for driving off-road).
  When a screenshot is ambiguous, look for the most mechanically plausible
  cause in the actual code before assuming the surface-level reading of the
  complaint is the right diagnosis.
