Да. И я бы делал это **не как “маленькую 3D игру”**, а как **маленький браузерный 3D FPS**, который по ощущениям напоминает упрощённый CS, но технически раза в 10 проще.

Для Яндекс Игр это нормальная техническая схема: WebGL поддерживается, а для realtime-мультиплеера веб-клиенту нужен сетевой транспорт вроде WebSocket и отдельный сервер — браузерный клиент сам полноценным игровым сервером быть не должен. ([Яндекс][1])

# Как сделать графику дешёвой

Вот здесь главное.

Не покупать дорогие AAA-модели.

Собирается пакет:

**Low Poly / Stylized FPS**

Из него:

* коробки;

# Самая важная часть — multiplayer

Вот здесь игра становится настоящим проектом.

Схема будет примерно такая:

```text
                 YANDEX GAMES
                       │
                       ▼
                Unity WebGL
                       │
                 HTTPS / WSS
                       │
               ┌───────▼────────┐
               │   MASTER       │
               │    SERVER      │
               │                │
               │ rooms          │
               │ players        │
               │ matchmaking    │
               └───────┬────────┘
                       │
              ┌────────┼────────┐
              ▼        ▼        ▼
           ROOM 1    ROOM 2    ROOM 3
            4v4       3v3       5v5
```

### Master Server

Он **не занимается всей физикой игры**.

Он занимается:

* созданием комнат;
* списком комнат;
* кодами;
* поиском игроков;
* запуском игровых серверов;
* закрытием пустых комнат.

### Game Server

Каждая игровая комната имеет игровой процесс:

```text
Room #K7X4P

Player 1
Player 2
Player 3
Player 4

VS

Player 5
Player 6
Player 7
Player 8
```

Game Server отвечает за:

* положение;
* стрельбу;
* попадания;
* здоровье;
* смерть;
* респавн;
* счёт;
* окончание матча.

И **не доверяет клиенту**.

Это важно: нельзя позволять браузеру сообщать серверу «я убил игрока». Сервер должен сам подтверждать попадание.

# Какой сетевой стек

Я бы не изобретал протокол самостоятельно.

Для клиента:

**Unity WebGL**

Для realtime:

**WebSocket/WSS**

Для backend:

**Node.js / TypeScript**

Для игровых комнат:

**Colyseus** либо собственный очень небольшой room-server.

Для начала мне больше нравится **Colyseus**, потому что он хорошо подходит именно под комнаты и realtime multiplayer.

Сервер:

```text
Node.js
   +
Colyseus
   +
WebSocket
```

База:

**PostgreSQL**

Но на самом первом MVP база вообще может быть минимальной.

---

# Почему не peer-to-peer

Потому что тебе нужны:

**серверы → список серверов → код комнаты → друзья → нормальные результаты → меньше читерства.**

WebGL имеет ограничения браузера на прямые сетевые сокеты, поэтому для такого проекта нормальный путь — WebSocket/WebRTC через веб-совместимый сетевой слой и отдельный сервер. ([Unity Документация][3])

**CREATE**

→ своя комната

**JOIN BY CODE**

### По срокам я бы закладывал так

**MVP:** 3–5 недель одним человеком при наличии опыта Unity.

**Первая приличная версия:** 6–10 недель.

**Версия, которую уже не стыдно активно продвигать:** 2–3 месяца.

Это именно оценка разработки, а не гарантия: сетевой FPS может сильно выбиться по срокам из-за сетевой синхронизации и WebGL-оптимизации.

И ещё важный момент: я бы **не начинал сейчас с карты, моделей и красивых меню**. Сначала нужно доказать самое опасное место проекта — **8 человек одновременно бегают, стреляют и видят одинаковый результат через WebSocket**. Если это работает, остальное уже в основном производство контента.
